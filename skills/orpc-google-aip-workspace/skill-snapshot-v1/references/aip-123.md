# AIP-123 — Resource Types (oRPC version)

Source: <https://google.aip.dev/123>

A resource **name** identifies a specific resource (`publishers/123/books/les-mis`). A resource **type** identifies the *kind* of resource (`library.example.com/Book`). The type is globally unique across services, which lets multi-service tools (Kubernetes-style controllers, generic API clients, GraphQL gateways, audit logs) reason about heterogeneous resources by category.

Most projects don't *need* resource types until they grow past one service. Once they do, the cost of bolting types on retroactively is high. Decide early.

## Type name format

```
{service-host}/{Type}
```

- `{service-host}` is the DNS-style host for the API service (`library.example.com`, `billing.internal.acme.dev`). Match what callers actually use.
- `{Type}` is the resource type in `PascalCase`, singular, alphanumeric only.

Examples:

```
library.example.com/Book
library.example.com/Publisher
billing.example.com/Subscription
billing.example.com/Invoice
```

The `{Type}` segment must match the name of the Zod schema / TypeScript type for the resource (`Book` ↔ `Book`). Matching is for human and tool consistency — if your schema is `Book` but your type says `Tome`, every audit reader has to translate.

## Where it lives in oRPC

Declare the resource type alongside the schema. A small `resource()` helper makes the relationship explicit:

```ts
// resources/book.ts
export const BookType = 'library.example.com/Book' as const

export const BookPattern = 'publishers/{publisher}/books/{book}' as const

export const Book = z.object({
  name: z.string()
    .describe(`Resource name. Type: ${BookType}. Pattern: ${BookPattern}.`),
  title: z.string(),
  authors: z.array(z.string()),
})

export type Book = z.infer<typeof Book>
```

Now any code that needs to dispatch on type (a generic audit logger, a webhook router, a permission checker) has a single source of truth.

## Patterns

The **pattern** is the name template with `{variable}` placeholders. It mirrors the path used in `.route({ path })`:

| Convention                                    | Rule                                                              |
| --------------------------------------------- | ----------------------------------------------------------------- |
| `publishers/{publisher}/books/{book}`         | Variables are snake/camel case, no `_id` suffix.                  |
| `[a-z][_a-z0-9]*[a-z0-9]`                     | Variable names match this pattern; start with a letter, ≥ 2 chars.|
| Variables are unique within a pattern.        | `users/{user}/users/{other}` ❌                                    |
| Collection identifier (e.g. `books`) is the **plural** of the lower-camelCase type.       | `Book` → `books`; `ApiKey` → `apiKeys`.                                                 |

When a resource has multiple legitimate patterns (e.g. a resource that can live under either of two parent types), declare both, with the most specific first.

## Singular and plural

For each type, define both:

- **Singular** — lower-camelCase of the type. `Book` → `book`, `ApiKey` → `apiKey`. Used as the URL-style path variable name and the field name when one of these is embedded as a reference.
- **Plural** — the plural form of the singular. `book` → `books`, `apiKey` → `apiKeys`. Used as the collection identifier in the pattern, and as the field name when a list of these is embedded.

```ts
export const BookType = 'library.example.com/Book' as const
export const BookSingular = 'book' as const
export const BookPlural = 'books' as const
```

Make these explicit constants in shared code if multiple services need to agree on them. The cost is small; the consistency win is large.

## Cross-service references

When another service references your resource, it uses the **full resource name** (AIP-122), and code on the receiving side typically dispatches on the type prefix:

```ts
// "//library.example.com/publishers/123/books/les-mis"
function parseFullName(s: string) {
  const m = s.match(/^\/\/([^/]+)\/(.+)$/)
  if (!m) throw new Error('not a full resource name')
  return { host: m[1], relative: m[2] }
}
```

The `host` tells you which service owns it. The pattern (declared once per type) tells you how to decode the relative name into structured parts.

## Practical guidance

- For a single-service oRPC app: declaring `*Type`, `*Pattern`, `*Singular`, `*Plural` constants is overhead you may not need. Start with `Type` and `Pattern` only; add the rest when a second service or a generic tool starts caring.
- For a multi-service org: codify the convention in a shared package (`@org/resources`) so every team's types and patterns are guaranteed to follow the rules. The package is mostly constants and types — small but high-leverage.
- For external/partner-facing APIs: surface the resource type in OpenAPI as the `x-resource-type` field on the schema, so client generators can preserve it.
