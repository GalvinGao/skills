# AIP-121 — Resource-Oriented Design (oRPC version)

Source: <https://google.aip.dev/121>

The core claim: an API is easier to learn, document, generate clients for, and evolve when it is shaped around **named resources** (nouns) rather than around procedures (verbs). oRPC has procedures, but you should still think of the procedures as operations *on resources*.

## What counts as a resource

A resource is anything the API exposes that has identity, has a lifecycle (it can be created, fetched, possibly updated, possibly deleted), and that the client refers to by name. `Book`, `User`, `Subscription`, `Workspace`, `ApiKey` are resources. `formatBook`, `sendEmail`, `recomputeBilling` are not — they are operations.

Anti-pattern: making your API a 1:1 reflection of your database schema. The database is an implementation detail; the resource model is a public contract. They will diverge, and that is healthy.

## The resource hierarchy

Resources live in collections, and collections can nest inside resources to form a tree. Example:

```
publishers/                       (collection of Publisher)
  publishers/{publisher}          (a Publisher)
    publishers/{publisher}/books/ (collection of Book under that Publisher)
      publishers/{publisher}/books/{book}
```

Two rules on hierarchy:

- The graph of resource references is a **DAG** — no cycles. If `A` references `B` and `B` needs to reference `A`, do it through an output-only computed field, not through a writable parent.
- Each resource has **one canonical parent**. A `Book` belongs to one `Publisher`, not three.

## Standard methods

Five operations cover most needs. Treat them as the default vocabulary.

| Method   | HTTP    | Input contains a resource? | Output is a resource?     |
| -------- | ------- | -------------------------- | ------------------------- |
| `list`   | `GET`   | no (parent + filters)      | array of resources        |
| `get`    | `GET`   | no (resource name)         | the resource              |
| `create` | `POST`  | yes (the resource body)    | the created resource      |
| `update` | `PATCH` | yes (partial resource)     | the updated resource      |
| `delete` | `DELETE`| no (resource name)         | nothing (or a tombstone)  |

Every resource **must** support `get` (so clients can read state after a mutation) and almost always `list` (the exception is a true singleton like a user's profile).

## Schema consistency

If the resource appears in the request *or* response of any method on the service, it must have the *same shape* everywhere it appears. Concretely in oRPC:

```ts
// Define the canonical resource schema once.
const Book = z.object({
  name: z.string(),               // "publishers/{publisher}/books/{book}" — see AIP-122
  title: z.string(),
  authors: z.array(z.string()),
  publishedAt: z.string().datetime().nullable(),
})

// Derive input shapes from it — do not hand-write parallel schemas.
const CreateBookInput = z.object({
  parent: z.string(),                                  // "publishers/{publisher}"
  bookId: z.string().optional(),
  book: Book.omit({ name: true }),                     // server assigns the name
})

const UpdateBookInput = z.object({
  book: Book.partial().required({ name: true }),
  updateMask: z.array(z.string()).optional(),
})
```

Deriving with `.omit` / `.pick` / `.partial` is what keeps the shape from drifting as the resource evolves. If you find yourself writing `CreateBookBody` and `BookResponse` by hand, you have already lost.

## Custom methods (when standard ones don't fit)

Some operations genuinely don't map to CRUD: `:archive`, `:publish`, `:rotateKey`, `:retry`. For those, model them as a custom method on the resource:

```ts
const archiveBook = os
  .route({ method: 'POST', path: '/publishers/{publisher}/books/{book}:archive' })
  .input(z.object({ name: z.string() }))
  .output(Book)
  .handler(/* … */)
```

Notes:

- Use `POST`, not a made-up HTTP verb. The `:verb` suffix on the path is what signals it's custom.
- Custom methods still operate on a resource (or a collection). `:sendEmail` floating with no resource is a smell — it probably belongs on `messages` as `create`.
- Reach for a custom method only after you've convinced yourself a standard method can't carry the meaning.

## Strong consistency after mutations

The control plane must reach steady state by the time a method returns success:

- After `create` returns OK, `get` on the new name must return the resource.
- After `update` returns OK, `get` must return the new field values.
- After `delete` returns OK, `get` must return `NOT_FOUND` (or a soft-deleted tombstone if the API supports that).

If the underlying work is genuinely asynchronous (provisioning a VM, training a model), return an `Operation` resource the client can poll. Do not return success and silently leave the system inconsistent — clients will sequence subsequent calls assuming success means done.

## Stateless interactions

Each request is independent. Don't require the client to call `prepare` before `do`. A resource can be addressed directly by its name from any request, with no setup. The server holds the persistent state; the client holds only application state.

## When to deviate

These rules optimize for a wide audience over a long time. If you're building a private API for one consumer that will be deleted in three months, the cost of following every rule may exceed the benefit. Apply judgment — but apply it *after* you've understood what the rule was protecting against.
