# AIP-126 — Enumerations (oRPC version)

Source: <https://google.aip.dev/126>

Enums are *small, stable, closed* sets of values. They are wonderful when used well and a maintenance burden when used badly. The rules below help you decide *whether* to use one and, if so, how to shape it so future additions don't break clients.

## When to use an enum

Use an enum when **all** of these are true:

- The values are discrete and finite.
- The set changes rarely — order-of-magnitude once a year or less.
- There isn't an existing standard for the values (BCP-47 language codes, IANA media types, ISO 3166 country codes — use the standard).
- An enum reads more clearly than a `string` or `boolean` at the call site.

If even one is false, prefer a documented `string`. It costs almost nothing today and avoids a breaking change later.

## When *not* to use an enum

- **Lots of churn expected.** Status codes for a workflow engine that's still being designed; tags applied by users; categories the product team keeps tweaking. Use `string` and document the set in the schema description.
- **A standard already covers it.** Don't invent `Language = { ENGLISH, FRENCH, ... }` when BCP-47 exists. Use `string` constrained to the standard's grammar.
- **Two values, no future need for a third.** A genuine boolean is fine. Default must be `false`.

## Zod shape

oRPC + Zod gives two reasonable encodings:

```ts
// 1. z.enum — concise, members are accessible via .enum.HARDBACK
export const Format = z.enum([
  'FORMAT_UNSPECIFIED',
  'HARDBACK',
  'PAPERBACK',
  'EBOOK',
  'AUDIOBOOK',
])

// 2. z.literal union — equivalent at runtime, sometimes clearer when you
//    want per-member JSDoc or to compose with other unions.
export const Format = z.union([
  z.literal('FORMAT_UNSPECIFIED'),
  z.literal('HARDBACK'),
  // …
])
```

Either is fine; pick one and stick with it within a project.

## Naming

- **UPPER_SNAKE_CASE** for every member, always.
- **Zero value = `<TYPE>_UNSPECIFIED`.** The first member is the type name plus `_UNSPECIFIED`. Its purpose is to be a default sentinel distinct from any meaningful value, so clients can detect "the server didn't set this" vs "the server set it to a real value".

  ```ts
  export const Visibility = z.enum([
    'VISIBILITY_UNSPECIFIED',     // ← sentinel; never a meaningful state
    'PUBLIC',
    'UNLISTED',
    'PRIVATE',
  ])
  ```

- **`UNKNOWN` as the zero value** is acceptable *when `UNKNOWN` is itself a meaningful, persistent state* (e.g. "we asked the user and they declined to answer"). Optionally prefix it (`STATUS_UNKNOWN`) when the enum lives in a shared package and member-name collisions are possible.

- **Member prefixes for package-level enums.** When an enum is shared across multiple resource schemas in the same package, prefix every member with the enum name to prevent collisions when it's translated to languages that hoist enum members to the top level (Go, C++, etc.):

  ```ts
  export const PaymentMethod = z.enum([
    'PAYMENT_METHOD_UNSPECIFIED',
    'PAYMENT_METHOD_CARD',
    'PAYMENT_METHOD_BANK_TRANSFER',
    'PAYMENT_METHOD_INVOICE',
  ])
  ```

  For enums declared *inside* a single resource schema and used only there, member prefixes are optional (and often visually noisy).

## Documenting the enum

Always note in the description whether the enum is **closed** (we don't expect new members) or **open** (we expect to add members, and clients should handle unknown values gracefully):

```ts
export const Format = z
  .enum(['FORMAT_UNSPECIFIED', 'HARDBACK', 'PAPERBACK', 'EBOOK', 'AUDIOBOOK'])
  .describe('Physical or digital format of a book. Open enum: future formats may be added; clients must tolerate unknown values.')
```

For open enums, document the fallback behavior clients should adopt (typically "treat as `FORMAT_UNSPECIFIED`").

## Falling back to string

When you decide an enum is the wrong tool, encode the field as a string in `kebab-case` with the allowed values listed in the description:

```ts
export const TagSchema = z.string().regex(/^[a-z0-9-]+$/)
  .describe('A user-defined tag. No enumeration — users may create any value matching ^[a-z0-9-]+$.')
```

If there's a *recommended* set you want callers to gravitate toward but don't want to enforce, document it without making it a constraint.

## Examples

```ts
// Good — small, stable, no standard exists for "what kind of book is this".
export const Format = z.enum(['FORMAT_UNSPECIFIED', 'HARDBACK', 'PAPERBACK', 'EBOOK', 'AUDIOBOOK'])

// Bad — language codes have a standard (BCP-47).
export const Language = z.enum(['LANGUAGE_UNSPECIFIED', 'ENGLISH', 'FRENCH', 'SPANISH']) // ❌
export const Language = z.string().regex(/^[a-z]{2,3}(-[A-Z]{2})?$/) // ✅ document as BCP-47

// Bad — high churn; product adds a new category every sprint.
export const Category = z.enum(['CATEGORY_UNSPECIFIED', 'FICTION', 'NONFICTION', 'POETRY']) // ❌
export const Category = z.string()                                                          // ✅ document allowed set
```
