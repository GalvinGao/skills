# AIP-122 — Resource Names (oRPC version)

Source: <https://google.aip.dev/122>

A resource's identity is its **name**: a slash-separated path like `publishers/123/books/les-miserables`. The name is the same string whether you see it in a URL, in a JSON body, or in a log line. It is the *one* identifier. Everything else (numeric primary keys, surrogate UUIDs, slugs) is an implementation detail.

In oRPC, the resource name *is* the path you put in `.route({ path })`, and it is *also* the value of the resource's `name` field. They are the same string.

## Name structure

Resource names follow URI path syntax (no leading `/`) and alternate between collection identifiers and resource IDs:

```
publishers/{publisher}/books/{book}
users/{user}/events/{event}
```

Rules:

- Segments separated by `/`. Non-terminal segments must not contain `/`.
- Use DNS-compatible characters where possible. Avoid Unicode unless unavoidable; if needed, use NFC.
- IDs are lowercase. Use kebab-case or alphanumeric, not camelCase or snake_case.

## Collection identifiers

The collection segments (`publishers`, `books`, `events`) are governed by:

- **Plural.** Use the plural form of the resource noun (`books`, not `book`).
- **camelCase.** Begin with a lowercase letter, ASCII only: `/[a-z][a-zA-Z0-9]*/`. Examples: `apiKeys`, `featureFlags`, `webhookDeliveries`.
- **Concise American English.** `subscriptions`, not `subscriptionRecords`.
- **Unique within a name.** A name like `users/{a}/users/{b}` is not allowed.
- **Singular = plural exceptions.** When the noun has no distinct plural (`info`, `moose`), use the singular form as-is — do not invent `infos` or `mooses`.

## Resource IDs

For client-supplied IDs (think slugs, account names):

- Pattern: `^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$` (lowercase, hyphens, 1–63 chars, starts with a letter, ends with a letter or digit).
- The API should validate this in the input schema:

  ```ts
  const ResourceIdSchema = z
    .string()
    .min(1)
    .max(63)
    .regex(/^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$/)
  ```

For system-generated IDs (UUIDs, snowflakes, opaque tokens): document the format and bounds in the schema description. Don't promise more structure than you can keep — if it might be a UUID today and a base32 string tomorrow, say "opaque, ≤128 chars".

## Nested collection shortening

When a child collection's noun would awkwardly repeat the parent's, you may shorten the **collection identifier** without renaming the resource type itself:

```
users/{user}/userEvents/{event}     ❌  redundant
users/{user}/events/{event}         ✅  collection shortened, type is still UserEvent
```

The TypeScript type / Zod schema is still `UserEvent` (or whatever expresses the meaning); only the path segment is shortened.

## The `name` field on the resource schema

Every resource schema has a `name` string field whose value is the full resource name. It is the canonical, stable identifier — the thing other resources reference.

```ts
const Book = z.object({
  name: z.string()           // "publishers/{publisher}/books/{book}"
    .describe('Canonical resource name. Server-assigned on create.'),
  title: z.string(),
  // ...
})
```

You may *additionally* expose:

- A `bookId` field (the last segment of the name) — mark it read-only in your description.
- A `uid` field with a UUID — also read-only — for cases where the slug changes but stable references are needed.

You must *not* expose:

- A tuple like `{ publisherId, bookId }` instead of a name. That is the anti-pattern resource names exist to prevent.
- A self-link URL like `https://api.example.com/v1/publishers/123/books/...`. The version belongs to the transport, not the identity.

## Why the field is named `name` and not `id`

Across the industry, `id` often means "the local primary key of this row". A resource name is more than that — it encodes the full hierarchical path. Reusing `id` invites callers to treat a 64-bit integer or UUID as the canonical identifier and to assemble paths client-side, which is exactly what you want to prevent.

## Parent fields on list / create

`list` and `create` operate on a collection, which is identified by its parent's resource name:

```ts
const ListBooksInput = z.object({
  parent: z.string(),                  // "publishers/{publisher}"
  pageSize: z.number().int().min(1).max(100).optional(),
  pageToken: z.string().optional(),
})

const CreateBookInput = z.object({
  parent: z.string(),                  // "publishers/{publisher}"
  bookId: ResourceIdSchema.optional(), // client may suggest one; server may override
  book: Book.omit({ name: true }),
})
```

If a resource has multiple possible parent types (e.g. `notes` under both `users` and `teams`), `parent` stays a string and the server validates the type prefix.

## References between resources

When one resource refers to another, reference it **by name** (a string), not by embedding the whole resource:

```ts
const Loan = z.object({
  name: z.string(),
  book: z.string(),    // "publishers/{publisher}/books/{book}" — a reference
  borrower: z.string(),// "users/{user}"
  dueAt: z.string().datetime(),
})
```

Why not embed `book: Book`?

- It complicates lifecycle: deleting the referenced resource leaves a dangling copy.
- It bypasses permissions: a user authorized to read `Loan` may not be authorized to read the embedded `Book`.
- It couples schemas: changing `Book` ripples into every resource that embedded it.

Naming convention for reference fields: the field name matches the resource type in `snake_case`/`camelCase`. Use a `_name` suffix only when the field name would otherwise be ambiguous (`crypto_key_name` because `crypto_key` could be confused with the actual key material). Use an `_id` suffix (`shelfId`) only when you're forced to expose the bare ID instead of the full name — and document why.

## Aliases

You may offer convenience aliases for common patterns:

- `users/me` → the authenticated user
- `organizations/-/repos` → repos across all orgs the caller can see

The alias is accepted in inputs. Responses still return canonical names. Don't let `users/me` appear as the `name` field on the returned `User`.

## Full resource names (cross-service references)

When a resource needs to reference one in another service, use the schemeless `//` form:

```
//library.example.com/publishers/123/books/les-miserables
//calendar.example.com/users/vhugo
```

The version is deliberately omitted — full resource names are expected to outlive API versions.
