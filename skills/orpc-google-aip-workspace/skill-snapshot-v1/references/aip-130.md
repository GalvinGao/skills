# AIP-130 — Methods (oRPC version)

Source: <https://google.aip.dev/130>

Once you've decided what your resources are (AIP-121) and named them (AIP-122), the next question is what operations they expose. AIP-130 is the *index* for that decision: it gives you a strict priority order and points you at the more detailed AIPs for each method shape.

## Priority order

When you need an operation, work down this list and stop at the first thing that fits:

1. **Standard methods** on a collection or resource (`list`, `get`, `create`, `update`, `delete`).
2. **Batch / aggregate** variants of standard methods (`batchGet`, `batchCreate`, `batchUpdate`, `batchDelete`, aggregated `list`).
3. **Custom methods** scoped to a collection or resource (`:publish`, `:archive`, `:rotateKey`, `:cancel`).
4. **Streaming methods** (server-stream, client-stream, bidi).

The order is by *consistency cost*. A standard method needs no documentation — every client knows what `get` does. A custom method needs a paragraph. A streaming method needs custom client code in every language. Don't pay a higher cost than the problem requires.

## Standard methods → oRPC

| Standard method | HTTP    | Path                              | Notes                                            |
| --------------- | ------- | --------------------------------- | ------------------------------------------------ |
| `list`          | `GET`   | `/{collection}` (under parent)    | Returns array; supports `pageSize`/`pageToken`. |
| `get`           | `GET`   | `/{collection}/{id}`              | Returns the resource.                            |
| `create`        | `POST`  | `/{collection}`                   | Body is the resource; server assigns `name`.     |
| `update`        | `PATCH` | `/{collection}/{id}`              | Body is the partial resource; `PATCH`, not `PUT`.|
| `delete`        | `DELETE`| `/{collection}/{id}`              | Returns nothing (or a tombstone).                |

A canonical oRPC router for one resource:

```ts
import { os } from '@orpc/server'
import * as z from 'zod'

const PageInput = z.object({
  pageSize: z.coerce.number().int().min(1).max(100).optional(),
  pageToken: z.string().optional(),
})

const Book = z.object({
  name: z.string(),
  title: z.string(),
  authors: z.array(z.string()),
})

const listBooks = os
  .route({ method: 'GET', path: '/publishers/{publisher}/books' })
  .input(PageInput.extend({ publisher: z.string() }))
  .output(z.object({ books: z.array(Book), nextPageToken: z.string().optional() }))
  .handler(async ({ input }) => { /* … */ })

const getBook = os
  .route({ method: 'GET', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({ publisher: z.string(), book: z.string() }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const createBook = os
  .route({ method: 'POST', path: '/publishers/{publisher}/books' })
  .input(z.object({
    publisher: z.string(),
    bookId: z.string().optional(),
    book: Book.omit({ name: true }),
  }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const updateBook = os
  .route({ method: 'PATCH', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({
    publisher: z.string(),
    book: z.string(),
    patch: Book.partial().omit({ name: true }),
    updateMask: z.array(z.string()).optional(),
  }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const deleteBook = os
  .route({ method: 'DELETE', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({ publisher: z.string(), book: z.string() }))
  .output(z.void())
  .handler(async ({ input }) => { /* … */ })

export const router = {
  books: { list: listBooks, get: getBook, create: createBook, update: updateBook, delete: deleteBook },
}
```

A few things worth calling out:

- **`PATCH`, not `PUT`.** Update is partial. A full-replace `PUT` is almost never what callers want and forces them to read-modify-write.
- **`updateMask`** explicitly names which fields are being changed. Without it, a missing field is ambiguous — "clear it" or "leave it alone"? With it, the answer is unambiguous.
- **`pageSize` + `pageToken`** for pagination (not `offset` + `limit`). Cursors survive insertions and deletions cleanly; offsets do not.
- **`bookId` is optional on create.** Server may generate one when not supplied. If your API only accepts server-generated IDs, drop the field entirely.

## Batch and aggregate methods

When clients routinely need to fetch or mutate many resources at once and you don't want them to make N round trips, expose a batch variant:

```ts
const batchGetBooks = os
  .route({ method: 'GET', path: '/publishers/{publisher}/books:batchGet' })
  .input(z.object({ publisher: z.string(), names: z.array(z.string()).min(1).max(1000) }))
  .output(z.object({ books: z.array(Book) }))
  .handler(/* … */)
```

The `:batchGet` suffix marks it as a custom method (because it doesn't fit `get`'s shape). Batch responses preserve input order and include all requested entries.

## Custom methods

Reach for a custom method when the operation genuinely doesn't fit any standard one:

- `:publish`, `:unpublish` — a one-shot state transition that's clearer than a partial update.
- `:rotateKey`, `:revoke` — a security operation with side-effects.
- `:cancel`, `:retry` — operations on a long-running job.
- `:resize`, `:render` — domain-specific transformations.

Shape:

```ts
const publishBook = os
  .route({ method: 'POST', path: '/publishers/{publisher}/books/{book}:publish' })
  .input(z.object({ publisher: z.string(), book: z.string() }))
  .output(Book)
  .handler(/* … */)
```

- Always `POST`. The `:verb` suffix on the path is the only signal that it's custom.
- Always scoped to a resource or collection. A method floating at the API root is usually a missing resource in disguise.
- Verb names are imperative, camelCase, and unambiguous in the resource's domain.

A custom method on a collection rather than a single resource uses the same shape with the collection path:

```
POST /publishers/{publisher}/books:exportCsv
```

## Streaming methods

oRPC supports event streams. They are a real tool — chat completions, log tailing, progress events — but they're the last resort because:

- Most HTTP clients don't handle streams as gracefully as request/response.
- Reconnection, ordering, and back-pressure all become client concerns.
- OpenAPI's expressivity for streams is limited; client generators degrade.

Use streaming when the alternative (polling, paging) imposes worse latency or worse cost than the streaming complexity itself.

## Long-running operations

If a logically synchronous operation takes long enough that the client shouldn't be holding the connection (model training, infra provisioning, bulk imports), don't keep it synchronous. Return an `Operation` resource the client can `get` to poll for completion:

```ts
const Operation = z.object({
  name: z.string(),               // "operations/{op}"
  done: z.boolean(),
  result: z.discriminatedUnion('kind', [
    z.object({ kind: 'pending' }),
    z.object({ kind: 'error', error: z.object({ code: z.string(), message: z.string() }) }),
    z.object({ kind: 'response', response: z.unknown() }),
  ]),
})
```

Returning an operation is consistent with AIP-121's read-after-write guarantee: the operation reaches a steady state (`done: true`) and the client can rely on that.

## Decision summary

```
Does a standard method fit?
  ├── yes → use it.
  └── no  → does a batch/aggregate variant fit?
            ├── yes → use it.
            └── no  → does a custom method (:verb) fit?
                      ├── yes → use it (POST, :verb suffix, scoped to resource).
                      └── no  → consider streaming, or rethink the resource model.
```
