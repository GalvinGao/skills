# AIP-130 — Methods (oRPC version)

Source: <https://google.aip.dev/130>

Most operations fit one of five standard methods. This file gives the canonical HTTP verb, path shape, and pagination convention for each one in oRPC. Stick to it whenever you can — standard methods need no documentation, generate cleanly into OpenAPI clients, and read identically across resources.

## The standard-method matrix

For a resource at `…/{collection}/{id}`:

| Standard method | HTTP    | Path                              | Notes                                            |
| --------------- | ------- | --------------------------------- | ------------------------------------------------ |
| `list`          | `GET`   | `…/{collection}` (under parent)   | Returns array; supports `limit`/`cursor`.        |
| `get`           | `GET`   | `…/{collection}/{id}`             | Returns the resource.                            |
| `create`        | `POST`  | `…/{collection}`                  | Body is the resource; server assigns identity.   |
| `update`        | `PATCH` | `…/{collection}/{id}`             | **Partial update.** See below.                   |
| `delete`        | `DELETE`| `…/{collection}/{id}`             | Returns nothing (or a tombstone).                |

Two things are easy to get wrong:

- **`update` is `PATCH`, not `PUT`.** A full-replace `PUT` is almost never what callers want — it forces them to read the current resource, merge their change, and write the whole thing back, and racing writers clobber each other's fields. `PATCH` with a partial body lets the client send only the fields it wants to change.
- **`list` is `GET`.** Using `POST` for a read breaks HTTP caching, breaks intermediary idempotency assumptions, and signals "this has side effects" to anyone reading the route.

## A canonical oRPC router for one resource

```ts
import { os } from '@orpc/server'
import * as z from 'zod'

const PageInput = z.object({
  limit: z.coerce.number().int().min(1).max(100).optional(),
  cursor: z.string().optional(),
})

const Book = z.object({
  name: z.string(),
  title: z.string(),
  authors: z.array(z.string()),
})

const listBooks = os
  .route({ method: 'GET', path: '/publishers/{publisher}/books' })
  .input(PageInput.extend({ publisher: z.string() }))
  .output(z.object({
    books: z.array(Book),
    nextCursor: z.string().optional(),
  }))
  .handler(async ({ input }) => { /* … */ })

const getBook = os
  .route({ method: 'GET', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({ publisher: z.string(), book: z.string() }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const createBook = os
  .route({ method: 'POST', path: '/publishers/{publisher}/books' })
  .input(z.object({
    publisher: z.string(),
    book: Book.omit({ name: true }),
  }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const updateBook = os
  .route({ method: 'PATCH', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({
    publisher: z.string(),
    book: z.string(),
    // PATCH semantics: every mutable field is optional. Fields the client
    // omits are left alone; fields the client sets to null clear them.
    patch: Book.partial().omit({ name: true }),
  }))
  .output(Book)
  .handler(async ({ input }) => { /* … */ })

const deleteBook = os
  .route({ method: 'DELETE', path: '/publishers/{publisher}/books/{book}' })
  .input(z.object({ publisher: z.string(), book: z.string() }))
  .output(z.void())
  .handler(async ({ input }) => { /* … */ })

export const router = {
  books: { list: listBooks, get: getBook, create: createBook, update: updateBook, delete: deleteBook },
}
```

## Pagination: `limit` + `cursor`

For `list`, use cursor-based pagination. The input takes a `limit` (max items in this response) and a `cursor` (opaque token from the previous response). The response returns the items plus a `nextCursor` if there are more.

```ts
const PageInput = z.object({
  limit: z.coerce.number().int().min(1).max(100).optional(),
  cursor: z.string().optional(),
})

const ListBooksOutput = z.object({
  books: z.array(Book),
  nextCursor: z.string().optional(),  // absent when no more pages
})
```

Why not `offset` + `limit`? Offset paging is slow on large tables (the database still scans the skipped rows) and inconsistent under writes (a row inserted between page 1 and page 2 is either skipped or duplicated). Cursors survive both cleanly.

Why not `pageSize` + `pageToken` (the Google-AIP names)? `limit` and `cursor` are the idiomatic oRPC + REST names, match the conventions already in use across most TypeScript ecosystems, and avoid forcing every reader to learn AIP-130's vocabulary.

`limit` should have a hard upper bound enforced by the schema (e.g. `.max(100)`); otherwise clients will ask for ten thousand and your database will hate you.
